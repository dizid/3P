Click → Result

What actually happens in the two seconds between your click and your score.

🎧 First, what is De 3 P's?

De 3 P's is a decision-support web app. Eight different frameworks — like 10-10-10 Rule, Regret Minimization, and Coin Flip Test — help you think through a hard choice. You fill out a short form, the app calculates a score, and gives you a recommendation.

Your history is saved so you can revisit decisions later. That's the whole pitch. The interesting part is what happens under the hood when you click.

The hook: You open the app. You pick “10-10-10 Rule”. You drag three sliders. A score appears. Feels instant, right? Here's what actually happens in those two seconds.

🎶 The record player

Think of the app as a vinyl record on a turntable. The grooves were pressed when the app was built — every bit of logic is already there, waiting. But nothing plays until the needle drops.

That needle is you. Every click, keystroke, or page load is a needle drop. The vibration then travels through a chain of parts — each one transforming the signal — until it finally comes out the speakers as a score.

📝 The formula, in plain English

The actual scoring lives in a seven-line getter inside ToolsStore.js. Left side: the real code from the repo. Right side: what each line is saying.

CODE 
tententenScore: (state) => {
  return Math.round(
    (state.tententen.feel10min * 0.15) +
    (state.tententen.feel10months * 0.35) +
    (state.tententen.feel10years * 0.50)
  )
},
PLAIN ENGLISH

Here's a live number the store will calculate and share with anyone who asks.

Round the answer to a whole number — no decimals on screen.

Your short-term feelings (10 minutes) count for 15%.

Medium-term feelings (10 months) count for 35%.

Long-term feelings (10 years) count for 50% — the future matters most.

Close the rounding. Total weight: 15 + 35 + 50 = 100%.

Done. Whenever any of those three numbers change, this formula reruns automatically.

Why this matters to you: If a user says “the long-term feels don't count enough,” you now know exactly which one line to change. You can tell your AI assistant: “in ToolsStore.js, in the tententenScore getter, change 0.50 to 0.70.” That's a surgical instruction, not a vague wish.

03

How the Pieces Talk

Reactivity, props, and events — the three ways our components stay in sync.

From a Cast to a Band

Module 2 introduced the cast — views, components, stores, the router. But a cast standing on stage does nothing. This module is about how they actually perform together.

🎻
The Marching Band

The drum major (the store) keeps time. When the tempo changes, every musician hears it instantly and adjusts. Trumpets cue trombones. Flutes answer clarinets. Nobody checks a whiteboard — they react to what they hear.

When you drag a slider in the app, the score at the bottom updates instantly. No refresh, no waiting. How? Three patterns: reactivity, props, and events. You’ll know all three by the end of this screen’s siblings.

Pattern 1 — Reactivity: The Tempo Everyone Hears

Reactive data is data Vue watches. Change it, and anything depending on it updates on its own. Think of it like a spreadsheet: edit cell A1, and every formula pointing at A1 recalculates without you lifting a finger.

CODE 
tententenScore: (state) => {
  return Math.round(
    (state.tententen.feel10min * 0.15) +
    (state.tententen.feel10months * 0.35) +
    (state.tententen.feel10years * 0.50)
  )
},
PLAIN ENGLISH

A live score called tententenScore. It reads three slider values from the store.

It’s a computed value — not stored, but calculated on demand from other values.

The moment any of the three sliders changes, this formula re-runs by itself.

Anywhere in the app that shows the score sees the new number immediately.

⚠
The #1 Bug: Data Outside the Reactive System

If you write let total = 0 at the top of a component, Vue doesn’t watch it. Change it — the UI shrugs. You need ref() or a store. When AI writes Vue that “looks right” but nothing updates, this is the cause 90% of the time.

Pattern 2 & 3 — Props Down, Events Up

Components talk in two directions. Parents hand data down to children as props. Children shout messages up to parents as events. It’s a strict one-way street, and the strictness is what keeps the app sane.

↓

Parent → Child (props)

What: A parent hands read-only data to a child.

Example: <ToolHeader title="10-10-10 Rule" />

Use when: The child just needs to display or use the value.

Don’t: Try to change a prop from inside the child — Vue will yell.

↑

Child → Parent (events)

What: A child fires a named signal the parent listens for.

Example: emit('update:modelValue', 80)

Use when: A user did something the parent needs to know about.

Don’t: Reach up and mutate the parent directly — emit instead.

↔

Anywhere ↔ Anywhere (store)

What: A shared box any component can read or write.

Example: toolsStore.tententen.feel10min = 7

Use when: Two distant components need the same data.

Don’t: Use a store for data only one component cares about.

Real code: a child that talks back

Here’s GutCheck.vue — the little “Lean Yes / Lean No / No Idea” picker. It receives a value and reports changes back, but never edits the value itself.

CODE 
const props = defineProps({
  modelValue: { type: String, default: '' }
})

const emit = defineEmits(['update:modelValue'])

const options = [
  { value: 'yes',    label: 'Lean Yes \u2713' },
  { value: 'no',     label: 'Lean No \u2717' },
  { value: 'unsure', label: 'No Idea ?' }
]

function select(value) {
  emit('update:modelValue', props.modelValue === value ? '' : value)
}
PLAIN ENGLISH

“The parent gives me a value called modelValue.” I can read it but I’m not allowed to change it directly.

“I promise I’ll send an event called update:modelValue” whenever the value should change. Think of it as filing paperwork.

Three button options the user can pick from. Just a plain list.

“Hey parent — please update the value to this.” I emit the new choice (or empty if the user clicked the same one twice).

v-model: the two patterns, combined

Props down + events up is such a common combo that Vue has a shortcut: v-model. One line, two-way binding.

CODE 
<GutCheck v-if="!showResult" v-model="gutFeeling" />
PLAIN ENGLISH

Show the GutCheck picker, but only if the result isn’t showing yet.

v-model="gutFeeling" means: “pass gutFeeling down as a prop, AND listen for the emit to update it.”

Two-way binding in one attribute. No manual wiring. This is the syntactic sugar that makes sliders feel magical.

The Outside World

The Lighthouse Keeper’s Radio

Module 3 showed the pieces talking to each other inside your browser — reactivity, props, events. All local, all instant. This module steps outside.

📡
The Keeper and the Radio

Most of a lighthouse keeper’s work is inside the lighthouse — polishing the lens, trimming the wicks, logging the weather. But when a ship calls on the radio, he talks to the outside. Each call drains battery, can fail from static, and takes real time. The lighthouse works fine without the radio — but it’s much more useful when the radio works.

The app talks to three outside services: Claude for smart advice, a Postgres database to remember your decisions across devices, and Stripe to charge money. Each call has a cost. Each one can fail.

💡
Why should I care?

When AI writes code that calls an external service, ask three questions: What happens if it fails? What if it’s slow? Does this cost money per call? Those three questions catch 80% of production bugs.

Offline-First: Save Locally, Sync Later

When you save a decision, the app does something clever: it saves it twice. Once to your browser instantly, once to the server in the background. If the server is unreachable, you never notice.

CODE 
// Always save locally
this.decisions.push(newDecision)
this.saveToLocalStorage()

// If authenticated, also save to server
if (authStore.isAuthenticated) {
  try {
    await fetch(`${API_BASE}/api/decisions`, {
      method: 'POST',
      headers: getHeaders(),
      body: JSON.stringify({
        tool: decision.tool,
        title: decision.decision || decision.title || 'Untitled Decision',
        description: decision.recommendation || null,
        data: decision.data || {},
        score: decision.score || null,
        adviceType: decision.recommendationType || null
      })
    })
  } catch (err) {
    console.error('Failed to sync decision to server:', err)
  }
}
PLAIN ENGLISH

Add the new decision to the in-memory list right now. No waiting.

Write it to the browser’s localStorage so it survives a refresh.

Only bother with the server if the user is logged in.

Try to send the decision to our API endpoint using fetch.

POST means “create a new thing,” not “just read something.”

Attach headers that prove who we are (includes the auth token).

Bundle up the decision as JSON and send it along.

If the server call fails — offline, slow, 500 error — don’t crash. Just log it.

The local save already worked. The user sees success either way.

✨
The aha moment

Saving never fails from the user’s perspective, because the local save is synchronous and instant. The server sync is a bonus — a gift to future-you on a different device. If it fails, you lose cross-device sync on that one entry, not the decision itself.

Case File #1 — The Nav That Wouldn’t Stay On Top

The symptom: when you navigated between pages, the page content slid over the top navigation bar for a fraction of a second. Ugly, disorienting, and — as you’re about to see — surprisingly stubborn.

📄
Four attempts. Same bug every time.

Here’s the real git log from this project. Each row is a commit that tried — and failed — to fix the same bug.

# Commit What was tried Result
1 df3e862 Make nav background opaque with !important ✗ Still overlapped
2 ff98905 Add isolate to <main> (force new stacking context) ✗ Still overlapped
3 unnumbered Set z-0 on <main> ✗ Still overlapped
4 7b69ec5 Set -z-10 on <main> ✗ Still overlapped (user very frustrated)
5 eec1314 Change nav from sticky to fixed; replace transform-based page transitions with opacity fades ✓ FIXED

Attempts 1–4 all poked at z-index or layering tricks. All four failed. Why?

The Confession

CSS has an invisible rule that AI almost never volunteers: transform creates a new stacking context. Our old page transitions used transform: translateX() for the slide-in effect. That transform built a brand-new layer — and z-index comparisons only work within the same layer.

💡
Why no z-index tweak could ever win

The nav was sticky — still in document flow, living in the page’s main stacking context. The transformed content had its own context, painted on top. No amount of setting z-index inside one context can beat an element in a different, higher context.

Three signals should have shouted “this isn’t a z-index bug”:

1

Same bug, every tweak

Four z-index values produced the identical symptom. If the variable actually mattered, the behaviour would have shifted.

2

Only during transitions

Static pages were fine. The bug only appeared while routes changed — pointing at the transition itself.

3

Transform is on the scene

The transitions used transform. CSS has a well-known rule: transform creates a stacking context. Google it — it’s the first result.

The Fix That Actually Worked

Two small edits, both from commit eec1314. The nav moves out of the document flow entirely, and the page transitions drop transforms and fade with opacity instead.

CODE 
<!-- src/App.vue -->
<nav class="fixed top-0 left-0 right-0 z-50 ... nav-bar"
     aria-label="Main navigation">
  ...
</nav>

<main id="main-content" class="pt-16 sm:pt-20" tabindex="-1">

/* src/style.css */
.page-enter-active,
.page-leave-active {
  transition: opacity 0.25s ease;
}
.page-enter-from { opacity: 0; }
.page-leave-to { opacity: 0; }
PLAIN ENGLISH

fixed top-0 left-0 right-0 — the nav is yanked out of the page’s document flow and pinned to the viewport. It no longer cares what happens inside <main>.

pt-16 sm:pt-20 — because the nav is out of flow, content would slip under it. So we add top padding to <main> to make room.

The transitions now fade with opacity only. No transform. No transform = no new stacking context. No overlap.

The whole class of bug is now structurally impossible — not just masked.

🎯
Name the invisible rule, and the fix appears

Attempts 1–4 treated a layering problem as a numbering problem. Once you see “transform creates stacking contexts”, every z-index fix looks absurd. The real move is to stop playing that game entirely.

How to Break an AI Bug Loop

When AI is suggesting cousins of fixes that didn’t work, stop typing “try again”. Try one of these moves instead.

🔄

Reframe the question

Stop asking “how do I fix X?” Start asking “what class of problem is this?” Nav overlap → stacking contexts. Stale data → reactivity. Flickering → layout shift.

👁

Look for the invisible rule

Every framework has unwritten rules AI doesn’t volunteer. Vue reactivity, CSS stacking contexts, React’s rules of hooks. Name the invisible rule and the fix usually follows.

📄

Check the git history

If AI is going in circles, look at the last 5 commits that touched this file. You’ll often see the same bug was fixed — or attempted — before.

⚡

Try the radical opposite

If you’ve tried z-index 10, 50, 100, 9999 — the problem isn’t z-index. Switch approach entirely (sticky → fixed, absolute → flex, useEffect → useMemo).

⚠
Spot the code smell

When AI suggests adding !important to “just force it”, treat that as a warning light. It almost always masks a deeper problem — wrong specificity, wrong layer, wrong selector.
